# Telegram-бот O.X. для продажи билетов

Бот продаёт билеты на O.X. HALLOWEEN NIGHT: 25 октября 2026, 20:00, клуб Fireball, 18+. Продажи закрываются **26 октября 2026 в 12:00 МСК**. Последний момент запроса возврата — **22 октября 2026 в 20:00 МСК включительно**.

## Что реализовано

- Выбор мероприятия и тарифа, email, ФИО, телефон, подтверждение заказа.
- Стандарт 790 ₽, VIP 1490 ₽, компания из шести человек 3600 ₽.
- Оплата на странице ЮKassa; данные для чека передаются вместе с платежом и возвратом.
- Выдача только по webhook после проверки платежа через авторизованный API ЮKassa.
- Шесть независимых QR для группового заказа. Фото с QR можно пересылать.
- «Мои билеты» с активными билетами, повторная отправка существующего QR.
- QR открывает веб-страницу без аккаунта. Кнопка и подтверждение необратимо погашают билет. Открытие страницы не погашает его.
- Полный возврат. Для группы — только весь заказ, если все шесть билетов активны.
- Заглушка промокодов; кнопка связи с менеджером. Нет истории заказов, админки и лимитов мест.

## Быстрый просмотр страницы билета без ключей

Зависимости уже установлены в локальную `.venv` при подготовке проекта. В PowerShell из папки проекта:

```powershell
.\.venv\Scripts\python.exe -m app.demo
```

Открой http://127.0.0.1:8000/demo. Это отдельный демонстрационный билет, без денег и отправки сообщений. Можно нажать кнопку погашения. Перезапуск демонстрации создаст новый билет. База демонстрации — `data/demo.sqlite3`; рабочая база другая. Демонстрация доступна только на этом компьютере.

## Запуск настоящего бота

Можно запустить меню до подключения ЮKassa: установи `PAYMENTS_ENABLED=false` в `.env` и заполни `BOT_TOKEN`. Мероприятия, тарифы и связь с менеджером будут доступны; оформление заказа и оплата отключены. Для включения продаж заполни реквизиты магазина и HTTPS-адрес, затем установи `PAYMENTS_ENABLED=true` и перезапусти процесс.

Нужны Python 3.13+, токен Telegram-бота, магазин ЮKassa и постоянный публичный HTTPS-адрес этого приложения. Токен и секретные ключи в переписку или Git отправлять не нужно.

### Установка на Windows

```powershell
cd C:\Users\rakza\Desktop\ox-ticket-bot
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
```

Команда копирования нужна один раз: не перезаписывай уже заполненный `.env`.

В `.env` заполни:

| Переменная | Значение |
|---|---|
| `BOT_TOKEN` | Токен, выданный BotFather |
| `PUBLIC_BASE_URL` | HTTPS-адрес сервера, например `https://tickets.your-domain.ru` |
| `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY` | Реквизиты магазина |
| `YOOKASSA_TEST` | `true` для тестового магазина; `false` для боевого |
| `RULES_URL`, `PRIVACY_URL`, `OFFER_URL` | Ссылки на документы; для тестового режима можно оставить пустыми |
| `RECEIPT_*` | Параметры чека, соответствующие настройкам магазина |

`BOT_USERNAME` определяется автоматически при запуске. `return_url` формируется из `PUBLIC_BASE_URL`: `/payment-return`. Не меняй публичный домен после продажи билетов: он уже записан в QR.

В личном кабинете ЮKassa настрой HTTP-уведомления:

- URL: `https://ваш-домен/webhooks/yookassa`;
- события: `payment.succeeded`, `payment.canceled`, `refund.succeeded`.

Запуск из папки проекта:

```powershell
.\.venv\Scripts\python.exe -m app
```

Telegram работает через long polling, отдельный webhook для Telegram не требуется. Приложение запускается **в одном экземпляре**. Не добавляй несколько workers или реплик.

Для Telegram используется системный HTTPS-прокси, если он настроен. При необходимости можно явно указать `TELEGRAM_PROXY_URL` в `.env`. При локальном запуске компьютер и приложение прокси должны оставаться включёнными.

### Постоянный сервер с Docker

На сервере с Docker Compose направь DNS домена на сервер и открой порты 80/443. Добавь в `.env` строку `DOMAIN=tickets.your-domain.ru`, укажи тот же домен в `PUBLIC_BASE_URL`. Затем:

```bash
docker compose up -d --build
docker compose logs --tail=100 bot
```

Caddy выдаст HTTPS-сертификат. БД хранится в отдельном Docker volume. Команду `docker compose down -v` не используй: она удаляет данные. Docker-конфигурация подготовлена, но на реальном сервере в этой работе не запускалась.

### Запуск без Docker Compose

На текущем сервере приложение развёрнуто отдельно от существующих сервисов, в `/opt/ox-ticket-bot`. Используется контейнер `ox-ticket-bot`, том `ox-ticket-bot-data` и автоматический перезапуск `unless-stopped`. HTTP доступен только на самом сервере: `127.0.0.1:8000`. Telegram работает через исходящее подключение и не требует открытого HTTP-порта.

При первом развёртывании:

```bash
cd /opt/ox-ticket-bot
docker build -t ox-ticket-bot:latest .
docker run -d --name ox-ticket-bot --restart unless-stopped \
  --env-file .env -e HOST=0.0.0.0 \
  -p 127.0.0.1:8000:8000 \
  -v ox-ticket-bot-data:/app/data \
  --log-opt max-size=10m --log-opt max-file=3 \
  ox-ticket-bot:latest
```

Проверка и управление:

```bash
docker logs --tail 50 ox-ticket-bot
curl -fsS http://127.0.0.1:8000/health
docker restart ox-ticket-bot
```

Для обновления кода сначала выполни `git pull --ff-only` и собери новый образ. Затем останови и удали **только контейнер** `ox-ticket-bot`, запусти его приведённой командой с тем же томом. Том с БД удалять нельзя. Изменения `.env` применяются при пересоздании контейнера; изменения `events.json` в этом варианте требуют пересборки образа.

На сервере пока включён режим `PAYMENTS_ENABLED=false`. Магазин ЮKassa настроен в `.env`, но тестовые оплаты требуют отдельного HTTPS-адреса и настройки webhook. Существующие сервисы на портах 443/8443 не изменяются.

## Как менять мероприятия

Редактируй `events.json` и перезапусти приложение. Можно добавлять несколько событий. Чтобы убрать событие из продажи, поставь `enabled: false` или удали его из JSON. Оплаченные заказы и билеты останутся в БД.

У каждого события и тарифа должен быть постоянный уникальный `id`. Даты задаются с часовым поясом, например `2026-10-25T20:00:00+03:00`. Цена указывается в рублях; `quantity` — сколько билетов выдавать за одну оплату. Изменение цены применяется к новым заказам: у уже оформленного заказа сохраняется его цена и описание.

Групповые билеты дают стандартный вход — это рабочее допущение из анализа ТЗ. VIP сохранён из исходного документа; точное время раннего входа не задано и не выдумывается. Время окончания мероприятия не задано. Билет становится использованным только после отметки, возвращённым — после успешного возврата; автоматического сгорания непогашенных билетов нет.

## Поведение при оплате и возврате

Заказ, запрос и ключ идемпотентности сохраняются до вызова ЮKassa. Повторные нажатия и уведомления не создают новые платежи или билеты. Для шести билетов в чеке одна позиция «Компания 6 чел» за 3600 ₽.

Возврат закрывает весь заказ. На время обработки возврата отметка о проходе недоступна; после подтверждения ЮKassa все билеты недействительны. При подтверждённой отмене возврата билеты снова доступны. Повторная попытка после окончательной ошибки возврата решается с менеджером, автоматического нового списания/возврата нет.

В момент закрытия продаж новые платежи не создаются и старые кнопки в боте не выдают ссылку на оплату. Уже выданная ссылка ЮKassa может оставаться доступной: если списание произошло **в 12:00 26 октября или позднее**, приложение оформляет полный возврат и не выдаёт билет. Проверяется время списания `captured_at`, а не время доставки webhook. Деньги по поздней ссылке могут кратковременно списаться перед возвратом.

При временном сетевом сбое запрос повторяется с тем же сохранённым ключом. Через 23 часа неопределённый запрос больше автоматически не повторяется: менеджер проверяет его в ЮKassa. Это исключает повторную операцию после окончания окна идемпотентности. Потерянные платежные webhook отдельной периодической сверкой не восстанавливаются — такой подсистемы по согласованному объёму нет.

После оплаты QR отправляются автоматически; при неудачной отправке выполняется повторная попытка. После аварийного перезапуска может повторно прийти сообщение с тем же QR, но новый билет не создаётся. Всегда можно открыть активные билеты в боте. Незавершённый ввод контактных данных при перезапуске надо начать заново через `/start`; оплаченные заказы не теряются.

## Минимальное обслуживание

Логи содержат номера заказов и типы ошибок, без контактных данных и QR-токенов. HTTP access log отключён, поскольку URL билета является его секретом. Не включай полное логирование URL на внешнем прокси.

Для резервной копии останови приложение и скопируй всю папку `data`; затем запусти его снова. В Docker копируй volume при остановленном контейнере bot. Для восстановления используй сохранённую БД и тот же публичный домен. Секреты хранятся только в `.env`.

Любой обладатель QR может необратимо отметить билет использованным — это согласованное поведение без аккаунтов. Публичная страница не показывает данные покупателя и не позволяет оформить возврат. Возврат доступен в Telegram покупателя.

## Структура

`app/bot.py` — диалоги и доставка; `service.py` — бизнес-логика; `db.py` — SQLite и миграция схемы; `provider.py` — API ЮKassa; `web.py` и `templates/` — публичные страницы и webhook; `events.json` — мероприятия. Основной процесс объединяет polling бота, HTTP-сервер и небольшой цикл обработки уведомлений/возвратов.

Интеграция сверена с официальными материалами: [уведомления ЮKassa](https://yookassa.ru/developers/using-api/webhooks), [справочник API ЮKassa](https://yookassa.ru/developers/api), [документация aiogram](https://docs.aiogram.dev/en/latest/dispatcher/dispatcher.html).
